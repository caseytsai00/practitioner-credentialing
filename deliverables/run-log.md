## Supersede note -- 2026-10-03

`scripts/engine.py:compute_status` had a precedence bug: it checked "are all six elements
resolved" before checking for an admitted Governing Body outcome, so a file the Governing Body
had actually approved could still read `in-verification` if this engine's own element tracking
had a lingering `finding` (e.g. a certification-lapse disposition that never explicitly cleared
it) that no human record had addressed. An admitted Governing Body decision is the office's real
authority and must govern the status regardless. Caught via `tests/test_e2e_batch_02.py` /
`tests/test_e2e_batch_03.py` against the real data (five real applications were affected:
APP-2026-005, APP-2026-010, APP-2026-018, APP-2026-026, APP-2026-039). Fixed in `scripts/engine.py`
with a new regression test (`test_admitted_governing_body_approval_governs_status_even_with_a_lingering_finding`
in `tests/test_engine_orchestration.py`), confirmed RED before the fix and GREEN after.

Because `deliverables/snapshots/batch-02.json` was already sealed (committed) with the buggy
result, its pre-fix bytes are preserved unchanged at
`deliverables/snapshots/batch-02.superseded-20261002-compute-status-fix.json`, and
`deliverables/snapshots/batch-02.json` was regenerated under a new `snapshot_id` via
`python3 scripts/run_batch.py --batch 2 --state deliverables/state/batch-01.state.json --force-resupersede`.
`deliverables/snapshots/batch-03.json` had been written to disk but never committed/sealed, so it
was simply regenerated fresh from the corrected batch-02 state -- no supersede copy was needed for
it, per the schema's own definition of "sealed" (committed to the handed-off repository).

## Supersede note -- 2026-10-03 (second fix)

`scripts/engine.py:evaluate_decisions` filtered decisions to only ones matching the application's
*current* revision before building `decision_records`, so a decision whose revision no longer
matched (e.g. an unrelated correction bumped the revision after the decision was issued) vanished
from `decisions[]` entirely -- no admitted:true, no admitted:false, nothing. This violates the
snapshot schema's own rule that a refused record stays in every later snapshot with its reason.
Caught via `deliverables/verification.md`'s independent recompute (the Governing-Body-approval
recount for batch 2 found 8 structurally-approval-shaped decisions in the raw data but only 7
applications with a non-null `approval_decision_id` in the snapshot; tracing the gap found
APP-2026-036's `GBD-2026-034` had simply disappeared). Fixed so every decision for an application
appears in `decision_records`; one naming a now-superseded revision is refused with an explicit
reason and queues a Medical-Services-Professional action item asking whether it still applies.
Regression test `test_decision_for_a_superseded_revision_is_refused_not_silently_dropped` in
`tests/test_engine_orchestration.py`, confirmed RED before the fix and GREEN after.

`deliverables/snapshots/batch-02.json` and `batch-03.json` were both already sealed (committed in
the batch-3 run's commit). Their pre-fix bytes are preserved unchanged at
`batch-02.superseded-20261003-decision-revision-fix.json` and
`batch-03.superseded-20261003-decision-revision-fix.json`, and both were regenerated under new
`snapshot_id`s via `--force-resupersede`.

the Clinical Director" (one of the five protected judgments: whether a finding is disqualifying),
but `scripts/engine.py` never actually implemented this trigger -- it was a genuine gap between
the design spec and the code, found by `deliverables/verification.md`'s own cross-check: batch 1's
`APP-2026-032` has a PPQ-2 answered "Yes", yet no element ever read `finding` for it; it only

`detect_ppq_findings` and wired it into `process_application` (overriding the `licensure` element

eligibility overrides. Two new tests: a unit test for `detect_ppq_findings` and an orchestration
test confirming the override fires even when every element would otherwise resolve, and that a
clearing Clinical Director disposition still resolves it afterward -- both confirmed RED before
the fix, GREEN after.

## Post-review fix round -- 2026-10-03

An independent whole-branch review (fresh reviewer, read-only pass over the full implementation
and the sealed snapshots) found 3 Critical and 7 Important issues, all in the sealed deliverable
itself, none hypothetical. Each was fixed with a regression test confirmed RED before the fix and
GREEN after; full detail for each is in `deliverables/verification.md`'s "Post-review fixes"
section. Summary:

1. **Critical** -- a disposition that explicitly declined to clear a licensure restriction
   ("present the file to the committee ... I make no recommendation on the privileges themselves")
   was read as clearing it, crossing the protected-judgment boundary the whole design is built
   around. Fixed in `parse_disposition_outcome`.
2. **Critical** -- a Governing Body decision's own `Conditions:` block (dated obligations) was
   dropped entirely, so `active-with-conditions` could seal with `monitored_conditions: []`.
   Fixed by parsing the block (`scripts/parsers.py`) and sourcing conditions from the admitted
   decision (`extract_monitored_conditions`).
3. **Critical** -- `activation.privileges` split only on `,`, leaving a `; `-separated list (used
   in 9 real decision documents) as one bogus code. Fixed in `scripts/parsers.py`.
4. **Important** -- a refused decision produced no action-queue item unless the refusal was a
   revision mismatch. Fixed: every refusal now queues one.
5. **Important** -- a second decision from the same body at the same revision was always refused
   as a "duplicate", which would have wrongly blocked the normal resolution of a deferral by a
   later approval. Fixed: the chronologically latest decision per body is the candidate for
   admission; an earlier one is refused as superseded by it, not as a duplicate.
6. **Important** -- a deferred or denied decision's stated `reason` never reached the action
   queue, leaving a file on a Governing Body hold with nothing telling a reader what's owed.
   Fixed: the reason is now queued.
7. **Important** -- the 3-attempts/21-days cadence, documented in `rules.md` as applying to
   references, was never wired into `resolve_references`. Fixed.
8. **Important** -- a `confirmed-with-discrepancy` verification reply was treated as no reply at
   all, leaving an otherwise-settled entry permanently `outstanding` even after the applicant
   amended the record to match. Fixed: it now counts as a reply.
9. **Important** -- the sticky terminal-state (withdrawn/discontinued) short-circuit discarded a
   file's `decisions`/`action_queue`/`monitored_conditions`, so a real item (e.g. "Notify
   applicant of discontinuance ...") vanished the batch after it was recorded. Fixed: these are
   now persisted in the ledger and carried forward.
10. **Important** -- `README.md` documented a `--batch 4` resume that would `KeyError`. Fixed by
    adding a `--as-of` CLI override and a clear blocked error instead of a crash.
11. **Important** -- `--force-resupersede` itself did no preservation, relying on a manual
    copy-aside step `SKILL.md` pointed to a README section that didn't exist. Fixed: the flag now
    automatically preserves the existing sealed bytes under a `superseded-<timestamp>.json` name
    before overwriting; `SKILL.md` describes this directly.

All three sealed snapshots were affected by one or more of these (batch 3 most, since most
real Governing Body activity is there) and were regenerated and resuperseded accordingly -- this
time via the now-automatic preservation in (11) rather than a manual copy. One consequence worth
flagging on its own: fix 1 (the disposition-clearing fix) correctly reclassifies APP-2026-015's
disposition as unable to be automatically interpreted (it no longer silently resolves a finding
the Clinical Director declined to clear), which correctly flips batch 3's result from `supported`
to `partial` -- this is the fix working as intended, not a regression.
