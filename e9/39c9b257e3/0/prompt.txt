### Issues

#### Critical (Must Fix)

**C1. A Clinical Director disposition that explicitly declines to clear a finding is read as clearing it — the engine decides protected judgment #2.**
`scripts/engine.py:568-584` (`parse_disposition_outcome`) adds the `clear` label on the phrase `"present the file to the executive committee"`. That phrase is an instruction to proceed *with the finding attached*, not a determination that the finding is immaterial. Real consequence in the sealed output — `office-exports/batch-03/dispositions/2026-05-06_disposition_APP-2026-015.md` says:

&gt; "The credential is current but it is **not full and unrestricted** while the stipulated agreement is in force. Present the file to the Executive Committee … **I make no recommendation on the privileges themselves.**"

`deliverables/snapshots/batch-03.json` seals APP-2026-015 as `licensure: "resolved"`, `packet_presentable: true` — while its own `monitored_conditions` still carries the board monitoring programme through 2027-08-31 and its `action_queue` still says the board action "needs Clinical Director review." The schema defines `resolved` as "verified and needs nothing further" and `finding` as "a fact the Clinical Director, **and then the committees**, must weigh" — i.e. a finding is meant to *survive* into committee review, which is precisely what this disposition ordered. The committees receive a clean packet with no licensure finding on it.

Note this is **plan-prescribed** (plan line 3044 lists that phrase as a `clear` signal), so it's a plan defect faithfully implemented, not an implementer deviation. Fix: drop `"present the file to the executive committee"` from the `clear` set — keep only `"no bar to appointment"` and `"sufficient and the file may proceed"`, which are actual determinations. Separately, `apply_dispositions:603-612` resolves **every** flagged element on a `clear`, not just the one the disposition discusses; no multi-element case fires in this data, but the blanket behavior is wrong (see I-note under Important).

**C2. The Governing Body's own `Conditions:` block is dropped entirely at the parser, so `monitored_conditions` is empty on the one conditional approval in the data.**
`scripts/parsers.py:83-99` enumerates fixed decision fields and never reads `Conditions`; `_HEADER_FIELD_RE` (`:35`) can't match the `- …` bullet lines anyway. `scripts/engine.py:676-686` (`extract_monitored_conditions`) sources conditions **only** from `board-action` letters matching `through YYYY-MM-DD`. `office-exports/batch-02/decisions/2026-04-14_GBD-2026-039.md` carries:

```
**Conditions:**
- Re-verification of the Washington licence before its expiry on 2026-12-31 — due 2026-11-30
- The Clinical Director's written concurrence on the 2021 practice gap explanation — due 2026-06-30
```

`deliverables/snapshots/batch-03.json` seals APP-2026-039 as `status: "active-with-conditions"` with `monitored_conditions: []`. The snapshot asserts a status that its own payload contradicts (schema: "active-with-conditions — active, with at least one monitored condition still running"), and two real dated obligations are lost — including a licence re-verification due 2026-11-30, which is exactly the failure mode the stakeholder opened the interview with ("a licence expires underneath it and I only notice when I happen to look"). The second condition is a protected judgment (#1) with a hard due date; it reaches the action queue only as a generic gap question with `due: null`.

**C3. `activation.privileges` is mangled wherever the office used `; ` to separate privilege codes — six sealed application entries carry a bogus code.**
`scripts/parsers.py:82` splits `Privileges` on `,` only. Nine decision documents use `; ` (e.g. `**Privileges:** PRIV-HOSP; PRIV-IM`). Result in the sealed snapshots:

| snapshot | application | `activation.privileges` |
|---|---|---|
| batch-02 | APP-2026-014, APP-2026-039 | `["PRIV-HOSP; PRIV-IM"]` |
| batch-03 | APP-2026-002, APP-2026-014, APP-2026-039 | `["PRIV-HOSP; PRIV-IM"]` |
| batch-03 | APP-2026-026 | `["PRIV-IM; PRIV-HOSP"]` |

The schema says `privileges` is "The privilege groups the approval named, **by their published codes**." `"PRIV-HOSP; PRIV-IM"` is not a published code, and no consumer can match it against `privilege-requests.csv`'s `privilege_code`. Fix: `re.split(r"[;,]", ...)`. **This is the fourth bug, and it is materially worse than the stale-action-item issue that was triaged away** — it is wrong data in the primary deliverable, not a redundant informational line.
